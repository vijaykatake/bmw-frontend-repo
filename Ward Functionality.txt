## 2. Database Structure and Relationships

### 2.1 Ward Table

The Ward Master uses the following table:

```sql
SELECT
    [WardId],
    [StationId],
    [WardName],
    [WardDescription],
    [IsWardActive],
    [IsWardDeleted],
    [AddedBy],
    [AddedDate],
    [UpdatedBy],
    [UpdatedDate]
FROM [BMWMaster].[Ward];
```

The following rules are mandatory:

- `WardId` is the primary key and an auto-increment/identity column.
- Use `WardId` to identify records for Update and Delete operations and for selecting the correct record in the grid.
- Do not send `WardId` as an insert value. The database generates it automatically.
- `StationId` is a foreign key referencing `[BMWMaster].[Station]`.
- `WardName` maps to the database column `WardName`.
- `WardDescription` maps to the database column `WardDescription`.
- `IsWardActive` determines whether the Ward is active.
- `IsWardDeleted` must not appear as a visible data-grid column or form field.
- `AddedBy` and `UpdatedBy` must contain the actual logged-in user's `UserId`, according to the existing authentication architecture.
- `AddedDate` uses the database default `GETDATE()`. Do not send it from the frontend.
- `UpdatedDate` is set by the stored procedure using `GETDATE()`. Do not send it from the frontend.

Inspect the actual table definition and stored procedure before implementation. Do not change the schema or invent additional columns.

### 2.2 Station Table

The Station table is static master data:

`[BMWMaster].[Station]`

There are currently two Station records. Station maintenance is outside this task. Do not create a Station Master screen, add Station CRUD functionality, or modify Station records.

The Ward Master must use the existing `StationId` relationship.

Display `StationName` in the Ward data grid, obtained through the stored procedure. The frontend must not implement its own database lookup or hardcode Station names.

## 7. Transaction Message Handling

Apply the previously established project-wide transaction-message standard without duplicating or replacing the existing notification system.

The relevant `ResultID` behavior is:

| ResultID | Meaning | Ward Master behavior |
|---|---|---|
| 201 | Exist | Show a red notification for an existing record. Do not refresh the grid or change the screen. |
| 202 | Add | Show a green success notification and refresh the grid. |
| 203 | Failure | Ignore for the current implementation. |
| 204 | Update | Show a green success notification, refresh the grid, and keep the updated Ward selected or positioned appropriately. |
| 205 | Delete | Show a red deletion notification and refresh the grid. |
| 206 | Error | Show the standard red error interface with Copy and Email controls. Preserve the current screen state. |
| 207 | Maintenance | Show the standard maintenance notification and log the user out after 10 seconds. |

For normal transaction notifications:

- Use the established top-right notification location.
- Use professional icons.
- Automatically dismiss after 5 seconds with a smooth fade-out.
- Respect the active theme.

Do not implement duplicate notification infrastructure.

For `ResultID = 206`, reuse the existing centralized exception logging architecture. If the controller throws an exception, log the applicable details in `[BMWLog].[ApiLog]` using the actual existing table schema and logging conventions.

The logical error response is:

- `ResultID = 206`
- `TransMessageId = 0`
- `TransMessage =` C# exception message
- `TransControl = N/A`

Follow the actual existing JSON serialization and response contract. Do not invent a new response structure.

The Email button is UI-only at this stage. Prepare or reuse the appropriate controller endpoint structure for future email functionality, but do not implement actual email sending.
